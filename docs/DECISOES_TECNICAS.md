# Inventário de decisões técnicas

Cada decisão registra as alternativas consideradas, a justificativa e o impacto (inclusive os negativos).

| ID | Decisão | Alternativas consideradas | Justificativa | Impacto / custo |
|---|---|---|---|---|
| D-01 | **Spring Boot 4 + Java 21**, com Spring MVC, Data JPA e Security (exigidos pelo enunciado) | versões anteriores do Boot | projeto base gerado pelo Spring Initializr; Java 21 é LTS | APIs novas (Spring Security 7, Hibernate 7); parte da documentação e dos exemplos da internet ainda é da geração anterior |
| D-02 | **H2 em arquivo** (`./database/academia`, schema `APP`, `AUTO_SERVER=TRUE`) | MySQL/PostgreSQL; H2 em memória | segue o exemplo do professor (Aula 16); roda sem instalar nada e persiste entre execuções | não é um banco de produção; concorrência e desempenho limitados. Trocar de banco exige apenas a URL e o driver |
| D-03 | **Esquema gerado pelo Hibernate** (`ddl-auto=update`) com restrições declaradas nas entidades (UNIQUE, índices e FKs nomeados) | Flyway/Liquibase com migrações versionadas; scripts SQL manuais | mesmo padrão do exemplo do professor; menos peças para o aluno explicar | não há histórico versionado do esquema; `update` não remove colunas antigas; sem `CHECK` no banco (faixas validadas no código) |
| D-04 | **Ids `Long`** com `IDENTITY` | `Integer` (usado no exemplo); UUID | `Long` evita estouro em tabelas que crescem (aulas, inscrições) e é o padrão do Spring Data | diferença pontual em relação ao exemplo do professor |
| D-05 | **Regras de negócio dentro da entidade `Aula`** (inscrição, lotação, transições, edição) e orquestração no serviço | regras só no serviço; regras só no controller | nenhum caminho de código (site, API, carga) consegue deixar a aula inconsistente; as regras são testáveis sem Spring (`AulaTest`) | entidade "rica" mistura dados e comportamento; exige disciplina para não contornar os métodos |
| D-06 | **Status como `enum` com mapa de transições** (`StatusAula.proximos()`) | tabela de status no banco; `String` livre; biblioteca de máquina de estados | transições válidas explícitas e testáveis; estados finais (`CONCLUIDA`, `CANCELADA`) sem saída; sem tabela extra | novo status exige alterar código e recompilar |
| D-07 | **Bloqueio otimista** (`@Version`) em `Aula` | bloqueio pessimista; nenhum controle | evita estourar a lotação com inscrições simultâneas sem travar leituras | a segunda requisição concorrente falha com HTTP 409 e o usuário tenta de novo. **Não há teste automatizado de concorrência** (veja `docs/TESTES.md`) |
| D-08 | **Conflito de horário do personal** verificado no serviço, comparando intervalos | restrição no banco (exclusão por intervalo); sem verificação | H2 não oferece restrição de sobreposição de intervalos; a regra é simples e testada nos limites (fim = início seguinte é permitido) | há uma janela de corrida entre a verificação e a gravação (duas criações simultâneas do mesmo horário); risco residual baixo para o porte do sistema |
| D-09 | **Formulários e DTOs separados das entidades** (`form/`, `dto/`) | receber/devolver a entidade direto | evita *mass assignment* (cliente enviar `id`, `status`, `versao`) e vazamento de dados (hash da senha); desacopla a API do mapeamento | mais classes e conversões |
| D-10 | **Filtros com Criteria API/Specifications** (`AulaSpecs`, `ClienteSpecs`), critérios combinados com E | JPQL com parâmetros opcionais; filtrar em memória; QueryDSL | consulta montada só com o que foi informado, sem concatenar SQL; filtra no banco; curingas `%`/`_` do usuário escapados | sem paginação: o resultado vem inteiro (aceitável para o volume atual) |
| D-11 | **Autorização por perfil no servidor** em `SecurityConfig` (ADMIN e OPERADOR); botões ocultados com `sec:authorize` só como conforto | só ocultar elementos na interface; anotações `@PreAuthorize` espalhadas | o enunciado exige proteção no servidor; regras em um só lugar, na ordem de avaliação, cobertas por `SegurancaIT` | a ordem das regras importa: uma regra nova mal posicionada pode abrir ou fechar rotas sem querer |
| D-12 | **Perfil como `enum`** (`Perfil`) | tabela `PERFIL` com permissões granulares (RBAC completo) | dois perfis com permissões distintas bastam para o enunciado | novos perfis ou permissões finas exigem evolução do modelo |
| D-13 | **Senhas com BCrypt**; contas de demonstração criadas só se não existir usuário; senhas por propriedade/variável | senha em texto; contas fixas no código | nunca guardar senha em texto; permitir trocar sem recompilar | as senhas padrão (`admin123`/`operador123`) são **só de demonstração** e estão documentadas; devem ser trocadas fora da apresentação |
| D-14 | **CSRF ligado no site** e ignorado apenas em `/api/**`; logout por `POST` | CSRF desligado; token também na API | protege formulários e logout; a API é consumida por clientes sem navegador com autenticação a cada requisição (HTTP Basic) | a API aceita HTTP Basic: apropriado para o trabalho, mas em produção usaria token (JWT/OAuth) e HTTPS |
| D-15 | **Console H2 desligado** | console habilitado para facilitar a depuração | o console expõe o banco inteiro; com Security ligado exigiria exceções de CSRF/frames | inspeção do banco pela ferramenta de banco de dados do IDE (`AUTO_SERVER` permite) |
| D-16 | **`EstadoContaFilter`**: consulta o banco a cada requisição autenticada para ver se a conta continua ativa | só validar no login; expirar sessões por tempo | desativar um usuário derruba a sessão já aberta na próxima requisição (comportamento testado em `FluxoCompletoIT`) | uma consulta extra por requisição (irrelevante neste porte; em escala usaria cache curto ou sessões revogáveis) |
| D-17 | **Erros da API em `ProblemDetail`** (`400` validação, `404`, `409` regra/concorrência/integridade); erros do site em mensagens na própria tela e página de erro | corpo de erro próprio; `422` para regras de negócio | padrão do Spring 6+; `409` expressa "o estado atual não permite esta operação" | clientes precisam tratar `409` como erro de regra, não de formato |
| D-18 | **Site renderizado no servidor (Thymeleaf)** + **API REST** que reaproveita os mesmos serviços | só site; SPA (React/Vue) | Thymeleaf é obrigatório no enunciado; a API facilita testes e integração sem duplicar regras | duas "portas de entrada" para manter coerentes (as regras ficam nos serviços/entidades justamente por isso) |
| D-19 | **Bootstrap 5 por CDN + tema próprio** (`custom.css`, paleta #1B365D, #005A9C, #60C1E5, #A0E0EF, contrastes conferidos) | WebJars/arquivos locais; framework CSS próprio | responsividade pronta e identidade visual consistente; contraste de texto ≥ 4,5:1 | exige internet para carregar o Bootstrap (para uso offline, trocar por WebJars) |
| D-20 | **Base de demonstração gerada com semente fixa** (`CargaDemonstracao`) | planilha real importada; dados digitados à mão | a mesma base em qualquer máquina, respeitando as regras (lotação, conflitos) e coberta por teste | os dados são fictícios; **a migração dos dados reais do legado não está implementada** (veja limitações no relatório) |
| D-21 | **Estratégia de testes em camadas**: unitários puros → unitários com Mockito → integração com Spring/H2 → fluxos ponta a ponta | só testes de integração; só testes manuais | feedback rápido nas regras e prova de integração nos fluxos; banco em memória isolado por classe de teste | os testes de integração são mais lentos; não cobrem a aparência visual (roteiro manual em `docs/evidencias`) |
| D-22 | **Integração contínua no GitHub Actions** | execução apenas local | registro público e repetível da execução dos testes | depende de o repositório estar no GitHub |
